## 발견한 실행/검증 문제와 조치

- 문법을 지정해도 출력 문자열 길이는 무제한이었다. 일부 선택지에서 따옴표를 닫지 못하고 반복 문자를 생성하다 토큰 예산에서 끝났다. Policy/Explanation의 textMaxChars·optionMaxChars를 GBNF 문법에도 연결했다.
- 공식 LlamaLib v2.0.5 C API와 호출 형식이 일치함을 확인했고, 설정한 문법을 Get_Grammar로 되읽어 확인한다. 전체 응답과 토크나이저로 실제 입력/출력 토큰 수, prefill/decode 시간, 상한 도달 여부를 기록한다.
- 짧고 자연스럽게 재사용할 수 있는 예시 응답까지 모두 복사 오류로 취급하는 오탐이 있었다. 최소 검사 길이를 JSON의 composition.exampleCopyMinChars로 분리했고 현재 12자다. 긴 문구의 정확한 복사 검사는 의미 판정이 아닌 보조 지표다.
- 선택지에 intent_0, text_0 또는 JSON 괄호만 출력하는 경우를 발견했다. JSON의 validation.invalidOutputPatterns로 검사한다. 기존 원문 자체가 해당 표현인 경우는 제외한다.
- Policy와 모듈은 중복 JSON 키를 거부한다. 모델 manifest에 남아 있던 오래된 GPU/문맥 수치는 제거하고 실제 설정 JSON의 resource 경로를 참조하도록 바꿨다.

API 근거: [LlamaLib v2.0.5 C API](https://github.com/undreamai/LlamaLib/blob/v2.0.5/include/LLM.h), [완료 요청 조립·응답 처리](https://github.com/undreamai/LlamaLib/blob/v2.0.5/src/LLM.cpp).

## 실제 모델로 제한 동작 확인

의도적으로 8자 상한을 준 제어 검사에서 카드 1개·선택지 4개가 구조와 길이를 지킨 JSON으로 끝났다. 입력 1,383토큰, 출력 48토큰이고 토큰 한도 도달은 false였다. 이 검사는 문장 품질 검사가 아니다. 별도의 literal 문법 검사와 세션 재사용 검사도 실제 Gemma에서 통과했다.

기본 길이 상한으로 도입과 표식 장면을 다시 실행한 시간은 각각 47.5초, 20.8초였다. 두 결과 모두 토큰 상한에 도달하지 않았으나, 예시 복사·역할 접두사 등으로 품질 검사는 실패했다. 도입의 각 작성 요청은 입력 1,159~1,520토큰으로 관찰됐으며, 이 사례의 역할 혼동을 문맥 초과만으로 설명할 근거는 없다.

이전에 문자열이 잘린 표식/꿈·seed=12345·예시 없음 조건도 동일하게 재검사했다. 새 문법에서는 작성 2회와 교정 1회가 모두 한도에 도달하지 않았고 JSON이 완성됐다. 39.1초가 걸렸으며 숫자 추가와 반복 대사 문제가 남아 합격으로 판정하지 않았다. 이전 34.1초보다 빠르지 않았다.
